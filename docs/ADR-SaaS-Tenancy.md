## 2) البدائل المُدارة (لماذا لم نخترها)

| البديل | ميزته | سبب الرفض الآن |
|---|---|---|
| **Schema-per-tenant** | عزل قوي، نسخ/حذف مستأجر سهل | 238 جدولاً × لكل عميل؛ كل استعلام يحتاج `search_path`؛ معظم كود `psqlFile`/الـmigrations يفترض `public`؛ توتر مع نظام الترحيل الحالي |
| **DB-per-tenant** | أقصى عزل، أسهل امتثال قانوني | تكلفة/مراقبة/نسخ لكل عميل؛ مناسب كخيار Enterprise فقط (القرار 2) |
| **عزل طبقة التطبيق فقط** (بلا RLS) | أسرع تنفيذاً | أي استعلام جديد ينسى `WHERE tenant_id` = تسريب صامت؛ لا حماية عند خطأ بشري — مرفوض أمنياً |
| **إعادة كتابة النظام** | — | مخالف للمبدأ الحاكم؛ النظام مُختبر 100% ولديه بوابات قلعة — نُضيف طبقة لا نهدمها |

## 3) العواقب (Consequences)

### إيجابية
- استضافة آمنة لعدد غير محدود من العملاء على نفس البنية.
- الأساس جاهز للفوترة (quota لكل مستأجر) وSSO والـwhite-label.
- كل الأصول الموجودة (MFA، WebAuthn، outbox، idempotency، DR، القلعة) تُستغل كما هي.

### سلبية / تكلفة
- ترحيل 238 جدولاً + فهارس إضافية ⇒ زمن تطبيق أطول وتخزين أكبر.
- كل استعلام جديد في المستقبل يجب أن يمر عبر سياق المستأجر ⇒ انضباط إلزامي في المراجعة.
- تعقيد إضافي في الاختبارات: كل اختبار حي يجب أن يزرع مستأجره (`tenant fixture`).
- الكاش والبث والكرونات تحتاج مفاتيح/غرف بمعرّف المستأجر قبل التوسع الأفقي.

### مخاطر محيطة (تخفيفها إلزامي)
| الخطر | التخفيف |
|---|---|
| تفعيل RLS قبل ضبط السياق ⇒ 0 صفوف | flag منفصل + اختبارات سياق + canary بمستأجر واحد |
| backfill خاطئ ⇒ تقارير منسوبة لغير صاحبها | مطابقة `count/sum` قبل/بعد لكل جدول + معاملة ذرية |
| نسيان بادئة tenant في الكاش/البث | فحص ثابت (gate) يمنع أي `io.emit` أو مفتاح كاش بلا بادئة |
| كسر عقود v3/Zod | الطبقة شفافة: نفس الـenvelope، المستأجر يُحقن في middleware فقط |

## 4) قيود التنفيذ (Non-negotiables)

1. **لا اتصال بـ`karim_erp` أثناء التطوير** — نسخة `karim_tenant_dev` فقط، بمنفذ/خدمة منفصلة.
2. **لا تعديل على ترحيل قديم** (القلعة: 175 بصمة sha256).
3. **لا SQL تخريبي** بلا نسخة احتياطية + `SELECT count(*)` + تأكيد صريح (قاعدة `erp-db-guardian`).
4. **`npm run audit:dry` بعد كل ترحيل** + حفظ النتيجة.
5. **خط أساس للأرقام** (count/sum لأهم الجداول) قبل أي ترحيل، ومطابقة بعده.
6. **لا ميزات SaaS جديدة قبل إغلاق بوابة المرحلة 1** (العزل أولاً).

## 5) القرارات المفتوحة المطلوبة من المالك (بوابة الدخول)

| # | القرار | التوصية | أثر التأخير |
|---|---|---|---|
| D1 | نموذج العزل (القرار 1/2) | مشترك + RLS، وDB منفصلة للـEnterprise | **يمنع بدء الترحيل** |
| D2 | السوق التالي بعد السعودية | مصر (ETA) — مواصفات أولية جاهزة | يؤخر محركات الضرائب (المرحلة 5) فقط |
| D3 | عملة الفوترة | SAR (ثم USD للخارج) | يؤخر المرحلة 4 |
| D4 | نموذج البيع | self-serve + sales-assisted معاً (خطط Free/Pro/Enterprise موجودة مسودة) | يؤخر المرحلة 4 |
| D5 | إقامة البيانات (Residency) | السعودية ومصر محلياً، وCDN عالمي للثابت فقط | يؤخر المرحلة 6 |
| D6 | SSO/SCIM من اليوم الأول؟ | SSO نعم للـEnterprise، SCIM لاحقاً | يؤخر المرحلة 3 |
| D7 | النطاق | subdomain مملوك لنا + نطاقات مخصصة لاحقاً | يؤخر تفاصيل الـmiddleware فقط (لا يمنع البدء) |

> **فور التوقيع على D1** أبدأ بترحيل `tenants` على النسخة المنفصلة + أول اختبار سلبي للعزل كـgate في القلعة.
