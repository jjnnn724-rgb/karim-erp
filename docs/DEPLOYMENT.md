# نشر KARIM ERP (ويندوز) — انقطاع مقيس + تحقق

## الأرقام الحقيقية (لا تقديرات)

| القياس | القيمة | كيف قِيست |
|---|---|---|
| زمن الإقلاع حتى قبول الطلبات | **~1.8s** | `scripts/measure-boot` style: استطلاع كل 200ms |
| **الانقطاع الفعلي عند إعادة تشغيل الخدمة** | **~2.0s** (2.0 / 1.8 / 2.5 / 1.8s في قياسات متتالية) | `scripts/deploy-verify.js` |
| زمن كتابة كاش الـSW | فوري | الـSW يخزّن نسخة جديدة عند تغيّر CACHE_VERSION |

> تصحيح مهم: كان يُقدَّر الانقطاع بـ"60 ثانية" — القياس الفعلي **~2 ثانية**.
> المصدر الحقيقي للانقطاع: إيقاف خدمة Windows + انتظار تحرير المنفذ (EADDRINUSE).

## الأمر

```bash
node scripts/deploy-verify.js              # نشر كامل: فحوص ← إعادة تشغيل ← قياس ← تحقق
node scripts/deploy-verify.js --dry-run   # الفحوص فقط
node scripts/deploy-verify.js --no-preflight   # نشر بدون بوابات (أثناء العمل الجاري)
```

**ما يفعله بالضبط:**
1. **فحوص ما قبل النشر** (تُوقف النشر إن فشل أيٌّ —和生产未被触碰):
   lint · أسرار · ميزانية المعالجات · سكربتات inline · بوابة التفويض ·
   معالجات ميتة · الحاويات · **اتساق إصدار الواجهة**.
2. `sc stop` + `sc start` (بلا انتظار طويل — التحكم في التوقيت بالاستطلاع).
3. **قياس الانقطاع**: أول فشل → أول نجاح (استطلاع كل 200ms).
4. **تحقق ما بعد النشر**: صحة الخدمة · صفحة التطبيق · رؤوس CSP (صارمة) ·
   **دور قاعدة البيانات (ليس superuser)** · عدد الترحيلات.
5. تقرير في `logs/deploy-<ts>.json`.

## نموذج الإصدار الفعلي (مهم)

- **ملفات الواجهة الثابتة تُخدَم فورًا** من شجرة العمل (الخدمة تعمل منها) ⇒
  أي تعديل في `frontend/` يصبح حيًّا **فورًا**، دون نشر.
- **العملاء لا يلتقطون التغيير إلا بعد رفع `CACHE_VERSION`** (كاش الـSW) ⇒
  **رفع إصدار الواجهة إلزامي مع أي تغيير** — ولهذا بوابة
  `npm run test:frontend-version` تفشل النشر إن تغيّرت الواجهة دون رفع.
  ```bash
  node scripts/frontend-version.js --bump   # يرفع النسخة ويحدّث البصمة
  ```
- **الواجهة الخلفية (backend)** تحتاج إعادة تشغيل الخدمة (jobs، مخططات) ⇒
  `node scripts/deploy-verify.js`.

## صفر انقطاع حقيقي (اختياري — يحتاج تعاون الـproxy)

الانقطاع ~2s مقبول أثناء التطوير،，但对 نسخة不能在 التبديل (السياسة ✗) أو
لعملاء يقطعون الطلبات أثناء التبديل (شبكة المطاعم ✗):

1. شغّل النسخة الجديدة على منفذ آخر:
   ```powershell
   $env:PORT=5001; $env:HOST=127.0.0.1; node backend/server.js
   ```
2. تحقّق منها: `https://127.0.0.1:5001/api/health` ⇒ 200.
3. بدّل الـproxy (nginx/aaPanel) من 5000 إلى 5001 ثم `nginx -s reload`.
4. أوقف النسخة القديمة بعد دقيقة.

> ملاحظة: الـproxy خارج نطاق هذا المستودع (aaPanel/Cloudflare) ⇒这一步 يدوي.

## التراجع
- **كود الواجهة/الخلفية**: `git checkout <commit> && node scripts/deploy-verify.js --no-preflight`.
- **قاعدة البيانات**: migrations تُطبَّق للأمام فقط؛ لكل migration أثر تراجعي معلّق
  في رأس الملف (مثل `113_app_role_activation.sql`) + نسخة `pg_dump` قبل أي تغيير ✓.
- **دور التطبيق**: `node scripts/activate-app-role.js --rollback` (استعادة `.env`) ✓.
- **النسخ الاحتياطية**: `npm run backup` (المجلد `database/backups` + مرايا خارجية) ✓.
