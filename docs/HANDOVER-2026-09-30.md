# دليل تسليم النظام — HANDOVER v4.8.0

**التاريخ:** 2026-09-30
**من:** كريم (التطوير)
**إلى:** الشركة المتلقية
**حالة النظام عند التسليم:** يعمل على جهاز الإنتاج (Windows) — كل البوابات خضراء

---

## 1. ما هو النظام

نظام إدارة مطاعم متكامل (Karim ERP v4.7+): كاشير POS، مخزون ومشتريات، موارد بشرية وحضور ببصمة، محاسبة، امتثال ZATCA، محرك واتساب، مزامنة مع نظام يارسوفت (Oracle)، بوابة موظف ذاتية مع **بصمة ذاتية مقيدة جغرافيًا وبصمة وجه** (جديدة — موثقة أدناه).

- **الواجهة:** PWA (HTML/JS مباشرة بدون خطوة بناء + وحدات ESM)
- **الخادم:** Node.js + Express (CommonJS) على المنفذ 5000 (HTTPS بشهادة محلية)
- **قاعدة البيانات:** PostgreSQL 18 (خدمة ويندوز `postgresql-x64-18`)
- **الجهاز:** Windows — الإنتاج يعمل عبر `scripts/serve.js` (مشرف يعيد التشغيل تلقائيًا)

## 2. التشغيل السريع

```bash
npm install                    # تثبيت التبعيات
node scripts/serve.js          # تشغيل كامل (يضمن PG + يفتح المتصفح)
node scripts/stop.js           # إيقاف
node database/scripts/backup.js  # نسخة احتياطية (مهم قبل أي تعديل)
```

**بوابات الجودة (كلها خضراء عند التسليم — لا تُنشر بدونها):**
```bash
npm run test:all        # eslint + typecheck + jest (932 اختبارًا)
npm run typecheck:strict  # فحص الأنواع الصارم على الوحدات المكتوبة
node scripts/test.js all  # الاختبارات الحية (jest + smoke + integration + workflow)
```

## 4. نظام البصمة الذاتية الجديد (الأهم للتشغيل)

موثق بالكامل في `docs/SPEC-employee-pwa-attendance-geofence-v1.md` (متطلبات) و`docs/PLAN-safe-rollout-playbook-v1.md` (خطة مراحل — S0–S8 منفذة ومُثبتة).

**التنفيذ:** مولود مغلقاً — التفعيل من الإعدادات بنقرة (ينعكس فورًا بلا إعادة تشغيل):
1. الإعدادات ← "البصمة الذاتية (Geofence)" ← زر **"أنا هنا — التقط الموقع"** (واقفًا في المطعم)
2. فعّل: البصمة الذاتية + الجيوفانس (+ بصمة الوجه بعد تسجيل وجوه الموظفين)
3. المرحلة التجريبية (S9): 5–10 موظفين أسبوعًا موازيًا لأجهزة البصمة

**طبقات الحماية المفعلة (كلها على السيرفر):** شبكة داخلية (L1، دائمًا) → 4 قراءات GPS يحللها السيرفر (تجميد/انتقال مستحيل/تشتت) → نطاق جغرافي → دقة وصلاحية الإشارة → بصمة وجه (متجه 128، بلا صور) → ربط جهاز → قفل بعد 5 رفضات/10 دقائق → تدقيق كامل في `punch_attempts`.

**حالة المفاتيح عند التسليم:** كلها **مغلقة** (`punch_portal_enabled=false`…) — التفعيل قرار إداري.

## 5. قواعد ذهبية للصيانة (مكتوبة بالدم — التزموا بها)

1. **انضباط كاش الواجهة**: أي تعديل على ملف واجهة يستلزم رفع `?v=` في وسم/استيراد **main.js ومع كل استيراد متأثر** — وإلا يعمل السيرفر بكود قديم بصمت (درس مؤلم موثق في git).
2. **الهجرات إضافية فقط** — لا تعديل/حذف هجرة قديمة أبدًا.
3. **لا نشر بدون نسخة احتياطية** (`node database/scripts/backup.js`) + Commit مستقل لكل خطوة.
4. **الترتيب في `server.js`**: dotenv قبل أي وحدة تقرأ NODE_ENV عند التحميل (كان سبب تعليق كامل سابقًا).
5. **`common/lan-discovery.js`**: يرد على `KRM_PROBE` فقط — أي "رد على الإعلانات" يعيد عاصفة CPU حرق نواة (سابقة موثقة).
6. **كل ميزة جديدة تولد مغلقة** بمفتاح في `punch_settings`/env (عقد السلامة G4).

## 7. الطريق المقترح للشركة (بعد التسليم)

1. **أسبوع 1**: تشغيل في بيئة الشركة + مراجعة docs/ + تشغيل بوابات الجودة
2. **TypeScript تدريجيًا**: الأساس جاهز — `tsconfig.strict.json` يحوي الوحدة المرجعية (0 أخطاء تحت `strict`)؛ أضيفوا ملفًا واحدًا كل أسبوع للقائمة (`checkJs` + JSDoc) — **لا تحويل شامل مفاجئ**
3. **إكمال بصمة الوجه**: مفعلة تقنيًا ومختبرة — تسجيل وجوه حقيقية + ضبط العتبة (0.55) + مرحلة تجريبية
4. **Docker (اختياري لاحقًا)**: `Dockerfile` + `docker-compose.yml` موجودان كنقطة بداية لكنهما **غير مُحقنين** على بيئة هذا الجهاز — الترحيل يستلزم: PostgreSQL داخل compose، تركيب الشهادات، شبكة LAN/broadcast للاكتشاف، أجهزة البصمة، ومجلدات `C:/HorusData`. يُنصح: بيئة Linux من الشركة + فترة توازٍ كاملة قبل التبديل
5. **تفعيل رسمي للبصمة الذاتية** (S10) بعد أسبوع pilot ناجح
