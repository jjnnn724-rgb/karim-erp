# ADR-003 — مفاتيح عدم التكرار وسياسة الإعادة

- **الحالة:** مقترح — بانتظار اعتماد المالك
- **التاريخ:** 2026-11-10
- **النطاق:** كل مزوّد في `integration_outbox`

## السياق

التسليم at-least-once (ADR-002) يعني احتمال وصول الرسالة مرتين. الجهات
الحكومية ترفض التكرار أو تُحتسبه خطأً، وبعضها لا يوفر idempotency key صريحًا.
نحتاج مفتاحًا حتميًا نستطيع إعادة إنتاج نفس القيمة بعد إعادة تشغيل الخادم.

## القرار

### 1) صيغة المفتاح

```
<provider>:<event_type>:<aggregate_type>:<aggregate_id>:<revision>
```

- `revision` تبدأ `1` وتزيد فقط عند إعادة إصدار مقصودة (إشعار دائن مصحح).
- المفتاح نصي ≤ 200 حرف، `UNIQUE` في قاعدة البيانات — لا فحص سباق في الكود.
- لا يحتوي تاريخًا عابرًا ولا معرّف عملية؛ إعادة المحاولة تستخدم نفس المفتاح.
- إعادة يدوية بعد dead-letter تُنشئ صفًا جديدًا بلاحقة `:retry:<n>`، وتبقى
  المحاولة الأصلية سليمة كإثبات.

### 2) تصنيف الردود

| الفئة | أمثلة | القرار |
|---|---|---|
| نجاح | 2xx مع قبول صريح | `delivered` + `success` |
| عابر | 408/429/5xx/مهلة شبكة | `failed` + إعادة وفق الجدول |
| دائم | 400/422 خطأ تحقق | `dead_letter` مباشرة + تنبيه |
| مصادقة | 401/403 | إيقاف المزوّد مؤقتًا + تنبيه + إعادة بعد تدوير الاعتماد |
| تعارض سلسلة | رفض PIH/ICV | `dead_letter` + مراجعة بشرية إلزامية |

### 3) جدول الإعادة

- المحاولة 0 فورية، ثم `min(3600s, 15s × 2^attempt)` مع jitter عشوائي
  حتى 20% لمنع تزامن الأسطول.
- `max_attempts` افتراضيًا 8؛ يصلح لكل مزوّد على حدة عند الحاجة.
- بعد الاستنفاد: `status='dead_letter'`، `attempts=max_attempts`.
- لا إعادة تلقائية بعد dead-letter؛ تحتاج `compliance.submit` (ADR-005).

### 4) الإثبات

- `response_sha256` لكل محاولة، و`response_excerpt` منقّى ومحدود بـ 2000 حرف.
- `last_error_code` نص قصير؛ رسالة الخطأ تُنقّى من أي Bearer/CSID/مفتاح.
- المحاولات كلها في `integration_events`؛ لا يُكتب فوق محاولة سابقة.

### 5) التزامن

- القفل عبر `FOR UPDATE SKIP LOCKED` + `locked_by` (معرّف العامل) و`locked_at`.
- قفل معلّق أقدم من 10 دقائق يُستعاد آليًا (عامل توفي أثناء الإرسال)؛
  إعادة الإرسال آمنة بسبب المفتاح الحتمي.

## العواقب

- تكرار النداء لا ينتج فاتورة مزدوجة على الطرفين.
- بطء مزوّد لا يوقف بقية المزوّدين (طوابير مستقلة بالمزوّد).
- نحتاج تعريف «قبول صريح» لكل مزوّد بعد رفع حالته إلى VERIFIED؛ لا نخمّنه.

## البدائل المرفوضة

- مفتاح عشوائي لكل محاولة: يلغي الحماية.
- إعادة غير محدودة: تُغرق الجهة وتخفي العطل الدائم.
- الاعتماد على UUID فقط: لا يكفي حين ترفض الجهة تكرار UUID بصيغة مختلفة.
