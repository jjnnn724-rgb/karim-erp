# 3. ACCOUNTING_ARCHITECTURE_AUDIT.md — تدقيق المعماري المحاسبي (READ-ONLY)

## 1. الخريطة المعماريّة الحالية
```
مصادر البيع/التشغيل ──► postJournal (backend/accounting-routes.js) ──► PostgreSQL (journal_entries/lines)
       │                                                            │
       ├─ pos (complete-sale, day-close) ── قيود Dr صندوق/بنك · Cr 4000 · Cr 2100 · Dr 5000/Cr COGS
       ├─ Yarasoft gl-bridge ── قيود Dr 1000 · Cr 4000 (أو Cr 3100 قبل cutover) — مفتاح idempotent = external_ref
       ├─ purchaseInvoices / procurement / subledger ── Dr 1150 / Dr 5000؟ · Cr 2000 (+ ضريبة مدخلات)
       ├─ dispatch / production / dept-transfer ── قيود تحميل داخلي متعدد الأقسام + تكلفة المصنع
       ├─ payroll / depreciation / inventory ── قيود تشغيلية
       └─ subledger-service (عملاء) ── قيد مبيعات آجل Cr 4000 + 2100، control 1300/1310
الفترات: accounting_periods ─ قفل posted عبر assertPeriodOpen (تُستدعى قبل أي ترحيل — داخل نفس مسار الطلب)
الضمانات القاعدة (095): توازن posted إجباري عند COMMIT · هوية القيد المنشور immutable
```

## 2. الضمانات الذرية الفعلية
- التوازن: النواة التطبيق تتحقق قبل الإدراج، والقاعدة تعيد فرضها عند COMMIT (Constraint Trigger مؤجل، ±0.01).
- عدم الازدواجية: `uq_journal_source (source_type, source_id)` + fingerprint يدوي (10 دقائق، نفس المستخدم/السطور/البيان) + بصمة GL bridge عبر external_ref.
- منع تعديل هوية القيد المنشور (095) — لكن **الحذف الصلب للقيود المنشورة ما زال مسموحًا** بالكود (موثقة كاستثناء في تعليق 095: مسارات purge تعتمد عليه) — **خطر RBAC/تتبّع**.
- الفترة المقفولة تُرفَض 423 من كل مسارات الترحيل (استدعاء موحد).
- أفضل effort بعد COMMIT للبيع — فشل القيد لا يُبطل البيع، وإنما يُسجَّل تحذيرًا؛ لا توجد طابور "قيود فاشلة" مضمون (اعتماد ضمني على sweep الجسر للإيراد فقط).

## 3. التكامل بين الوحدات والحسابات — الملاحظات
- **المبيعات**: Cr 4000 موحد (لا حساب تفصيلي لـ Dine-in/Takeaway/Delivery في القيد الفعلي رغم وجود 4010–4050 في الشجرة) — القيود لا تستخدم الحسابات التفصيلية الجديدة.
- **ضريبة المبيعات**: Cr 2100 دائمًا؛ لا فصل "ضريبة مخرجات" عن "أجزاء تسوية".
- **المشتريات**: Dr 1150 ضريبة مدخلات · Cr 2000 (AP) — لا استخدام لـ 2010..2040 (موردين تفصيلي) ولا sub-supplier subledger (فقط جدول suppliers + aging على 2000 مجمّع).
- **المخزون**: حساب واحد `1200` للترحيل الفعلي رغم وجود 1210–1250 في الشجرة — تفصيل التكلفة غير مرتبط بالقيود.
- **الإهلاك**: Dr 6600 / Cr 1520 (تجميعي) — لا فصل لكل أصل/مركز تكلفة على حساب مستقل (الصحيح تصميميًا: حساب إهلاك واحد + تحليلي مركز تكلفة — مقبول عالميًا) لكن `1520` تمركز ضمن 1500 الأصول غير المتداولة (صحيح).
- **الرواتب**: Dr 6000 / Cr 2200 عبر post-payroll — لا تفصيل بدلات/استقطاعات (لا GOSI 2130، لا تأمينات طبية في القيد الواحد).
- **التحويلات الداخلية**: `4000/5000` بين الأقسام مع مراكز التكلفة (مقبول تحليليًا، غير قياسي في GL كلاسيكي — يحتاج مركز تكلفة + ملاحظات).
- **العملاء**: `subledger-service` يرحّل مبيعات آجلة Cr 4000 + 2100 مع control_account من `customers.control_account_code` (1300/1310) — سليم.
- **AR/AP reconciliation**: view `view_ar_reconciliation` MATCHED · `view_ap_reconciliation` **DISCREPANCY −706,091.83** — لم يُحلَّل بعد، ويجب عدم "تسويته بترحيل" دون تحقيق.

## 4. الازدواج/التكرار/التعارض (ما بعد الصدمة 2026-10-05/06: 1,447 قيدًا / 129,182.64)
إصلاح الجسر بـ external_ref تم فعليًا، والتكرار الحالي في `journal_entries` غير مرصود بأدلة بعد ذلك، لكن الخطر البنيوي قائم: أي مسار posting جديد لا يمر عبر postJournal/external_ref يكسر المبدأ. **لا توجد فهرسة على `(source_type, source_id)`؟** — موجودة: `uq_journal_source` unique + index. جيد.

## 5. ما ينقص لمعماري "عالمي" (مفصل في 9/10)
- جدول `account_mapping(module, operation, account_code, role, priority, active)` بدل ثوابت متناثرة في الكود (40+ موقع).
- وحدة Posting واحدة (Posting Engine) بعقد واحد (source_type موثقة + idempotency key إلزامي) بدل نمط "كل وحدة ترحّل بنفسها".
- فصل صريح: ترحيل تلقائي = service account (`system:yarasoft-gl-bridge` logged كهوية نظام موثقة) بدل `created_by NULL` — الكود الحالي يسمح NULL للمناديات النظامية (انظر 095 ملاحظة identity: لا قيد "created_by ليس NULL" في القيد اليدوي؟ غير مطبق — فجوة حوكمة).
- Lock سياقي: الفترة + القيد داخل نفس transaction عند الترحيل (حاليًا `assertPeriodOpen` ثم insert في معاملة منفصلة — **TOCTOU محتمل**: فترة تُقفل بين الفحص والترحيل — منخفض الاحتمال لكن واقعيًا موجود).
- لا توجد مسودة قيود إنتاجية ذات موافقة متعددة (الموافقة موجودة للمسودات لكن لا تُفرض على اليدوي النشر المباشر).
- لا توجد "من أنشأ / من راجع / من اعتمد / من رحّل" — فقط created_by + approved_by.

## 6. قابلية التشغيل بلا Oracle
نعم للمحاسبة الداخلية (انظر التقرير 4 و5). أكبر قيد: **الإيراد التشغيلي لا يدخل الدفتر دون الجسر**، لأن البيع الفعلي من الكاشير. هذا يجب أن يكون قرارًا رسميًا: إما الجسر (كما هو) أو البيع المحلي (POS محلي) كمسار أول.
