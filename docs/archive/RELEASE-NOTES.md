# مطاعم الشرفه العالمي — حزمة التسليم الحديثة

هذه الحزمة هي أحدث نسخة فعلية من نظام حورس ERP بعد إضافة تقرير مبيعات الكاشير حسب الصنف، وقائمة الأوردرات الكاملة، والطباعة، والمقارنة بين البيع الفعلي وإنتاج المطبخ.

## التشغيل

شغّل PostgreSQL ثم نفّذ `node scripts/start.js` من مجلد المشروع. يقوم النظام بتطبيق الترحيلات الإنتاجية المعلقة وفق إعدادات البيئة المحلية، ثم يشغّل خادم ERP على المنفذ المحدد في `.env`، والافتراضي هو 5000.

## إعداد البيئة

انسخ `.env.example` إلى `.env` واملأ إعدادات PostgreSQL المحلية والقيم السرية قبل التشغيل. لا تحتوي هذه الحزمة على `.env` أو كلمة مرور PostgreSQL أو نسخ احتياطية لقاعدة البيانات.

## تقرير مبيعات الكاشير

من شاشة الكاشير افتح **سجل الفواتير**. يعرض قسم **مبيعات الأصناف الفعلية** إجمالي الكمية المباعة، وعدد الفواتير، وصافي المبيعات، والضريبة، والأقسام. يعتمد التقرير على الفواتير الصادرة فقط ويستبعد الملغاة. تظهر المقارنة مع إنتاج المطبخ عند وجود دفعات إنتاج مسجلة للصنف.

## ملاحظات أمنية

لا ترفع ملف `.env` أو أي ملف اعتماد إلى مستودع عام. استخدم Cloudflare Tunnel للوصول الخارجي بدل فتح منفذ PostgreSQL أو منفذ الخادم مباشرة على الإنترنت، واحتفظ بنسخ PostgreSQL الاحتياطية خارج حزمة التطبيق.

## سكريبت karimabdelhamed

يمكن استخدام `node scripts/karimabdelhamed.js setup` لتهيئة PostgreSQL وإنشاء قاعدة `karim_erp` عند عدم وجودها، ثم تطبيق الترحيلات الإنتاجية وتهجير كلمات المرور إلى bcrypt. استخدم `node scripts/karimabdelhamed.js start` لتهيئة ما يلزم ثم تشغيل الخادم على `0.0.0.0` حتى تصل إليه أجهزة الموظفين عبر عنوان IP الخاص بالخادم.

لبناء نسخ Windows استخدم `node scripts/karimabdelhamed.js build-exe`، أو شغّل `karimabdelhamed.bat build-exe` على Windows. ينتج الأمر نسخة NSIS Installer ونسخة Portable وفق إعدادات Electron Builder. وعلى جهاز الموظف يمكن استخدام `node scripts/karimabdelhamed.js client SERVER_IP` لفتح واجهة الكاشير من خادم الشبكة.

السكريبت لا يحذف قاعدة بيانات موجودة ولا ينفذ تصفيرًا أو reset. يجب السماح لمنفذ HTTP الخاص بالخادم داخل شبكة LAN فقط، وعدم فتح منفذ PostgreSQL للشبكة.

## إصلاح سكريبتات التهيئة والتشغيل — 2026-08-23

تم إصلاح سبب فشل التشغيل الأول: كانت بعض الأوامر تستخدم `node` و`npm` من PATH بدل مسار Node الفعلي، وكانت كلمة مرور PostgreSQL المولدة لا تُعاد إلى السكريبت الأب. أصبح التشغيل يستخدم `process.execPath` و`npm.cmd` على Windows، ويحفظ كلمة المرور محليًا دون طباعتها، ثم يعيد قراءتها بعد تشغيل PostgreSQL.

أصبح `setup` يوقف التهيئة عند فشل الترحيلات أو تشفير كلمات المرور بدل إكمال تشغيل ناقص. كما أصبح `start` يستخدم المسار الرسمي مع فحص الصحة والإيقاف الآمن، وتم إصلاح فتح رابط عميل الشبكة على Windows.

الأوامر الموصى بها على Windows:

```bat
node scripts\\karimabdelhamed.js setup
node scripts\\karimabdelhamed.js start
node scripts\\karimabdelhamed.js build-exe
```

إذا ظهر خطأ تنزيل PostgreSQL على Linux، يمكن استخدام PostgreSQL مثبتًا على النظام أو وضع PostgreSQL Portable يدويًا داخل `database/bin` قبل التشغيل. لا يتم حذف قاعدة البيانات أو تنفيذ reset تلقائيًا.

## تحديث إصلاح السكريبتات — 2026-08-23

تم إصلاح اكتشاف PostgreSQL النظامي في Linux وWindows، والتحقق الصحيح من `PG_VERSION` بدل اعتبار أي ملفات داخل مجلد البيانات قاعدة مهيأة. إذا وُجدت ملفات غير مكتملة، يحفظها السكريبت في مجلد `data.preinit-*` بدل حذفها، ثم ينشئ عنقودًا نظيفًا.

تمت مزامنة `DB_PORT` و`listen_addresses` و`unix_socket_directories` داخل `postgresql.conf`، وإصلاح حفظ كلمة المرور المولدة، وجعل الترحيلات وتهجير كلمات المرور حالات فشل حقيقية توقف التهيئة. كما تم إصلاح الإيقاف حتى لا يترك عملية Express معلقة.

تم اختبار `setup` بنجاح على PostgreSQL 16، وتطبيق الترحيلات من 001 إلى 027، والتحقق من bcrypt، ثم تشغيل خادم Express على منفذ LAN واختباره بـ HTTP 200 وإيقافه دون عمليات متبقية.

## تدقيق صلاحيات أذونات الصرف — 2026-08-23

تم تقوية الصلاحيات على مستويي الواجهة والخادم: يستطيع دور `kitchen` قراءة سجل الأذونات وإنشاء طلب صرف جديد، بينما لا يستطيع اعتماد الطلب أو رفضه أو تعديل حالته عبر مسارات CRUD العامة. أصبحت صلاحيات الاعتماد والتعديل محصورة في `admin` و`manager` و`warehouse`، كما بقيت عمليات المخزن والمرتجعات خارج صلاحية المطبخ.

أُجري اختبار حي بمستخدم مطبخ مؤقت: نجحت القراءة والإنشاء، وأُعيد HTTP 403 عند محاولة الاعتماد عبر `/api/warehouse/dispatches/:id/approve` وعند محاولة تغيير الحالة عبر `PUT /api/dispatches/:id`. تم حذف المستخدم وطلب الاختبار تلقائيًا بعد انتهاء الفحص، ولم تُترك بيانات اختبار.

ملف الاختبار القابل لإعادة التشغيل هو `scripts/test-dispatch-permissions.mjs`، ويُشغّل بعد بدء الخادم باستخدام `KARIM_TEST_PASSWORD` لحساب الإدارة.

## دورة الصرف الموقعة والجرد متعدد الفترات — 2026-08-23
تم إغلاق دورة إذن الصرف إلكترونيًا على مستوى الخادم والواجهة: يبدأ الطلب بحالة `pending` ولا يمكن إنشاء طلب معتمد عبر CRUD العام، ويعتمد المخزن أو الإدارة الإذن عبر توقيع إلكتروني مضبوط الصيغة وهاش SHA-256 محفوظ، مع منع دور المطبخ من الاعتماد أو الرفض وإرجاع HTTP 403 عند المحاولة.

تم توسيع جرد المخزن والمطبخ ليدعم يوميًا وأسبوعيًا وشهريًا وسنويًا وفترة مخصصة، مع حفظ تاريخ البداية والنهاية، ودورة مسودة ثم عد ثم إرسال بتوقيع ثم اعتماد بتوقيع ثم تسوية ذرية لفروقات الكميات والقيم في دفتر المخزون. تعرض الواجهة اسم الدورية ونطاقها، وتمنع اعتماد الجرد غير القابل للاعتماد أو تكرار التسوية.

أضيف الترحيل التوافقي `031_inventory_audit_actor_signatures.sql` لحقول مُعدّ الجرد وتوقيع الإرسال، مع اختبار `scripts/test-signed-workflows.mjs` وأمر `npm run workflow`. نجحت اختبارات الوحدات بعد التعديل: **267/267**، ونجح Smoke Test، ونجح Integration Test: **49/49**، ونجح Signed Workflow Test: إنشاء المطبخ، منع اعتماده **403**، اعتماد المخزن بتوقيع، استلام المطبخ بتوقيع، منع الاستلام المكرر **409**، جرد المخزن السنوي، وجرد المطبخ بفترة مخصصة.

## إغلاق أمان الإنتاج وحزمة Windows — 3.1.1

أزيلت كلمة المرور العامة `admin/1234` من تهيئة قاعدة البيانات. في التشغيل الأول تُنشأ كلمة مرور مسؤول عشوائية محليًا داخل ملف محمي خاص بحساب Windows، ويُلزم النظام المستخدم بتغييرها قبل فتح أي صلاحية تشغيلية. تُدار الجلسات عبر JWT لمدة 24 ساعة، ولا تمنح صلاحيات الأدوار قبل إتمام تغيير كلمة المرور.

تم تنظيف نموذج البيئة من كلمات المرور والمفاتيح الوهمية التي قد تبدو قابلة للاستخدام. يبدّل setup أي قيمة نموذجية قديمة بكلمة PostgreSQL ومفاتيح JWT عشوائية محلية، ولا تحتوي الحزمة على ملف `.env` فعلي أو بيانات قاعدة أو نسخة احتياطية.

تم تحديث Nodemailer وUUID وإضافة `package-lock.json` لإعادة بناء حتمية. أظهر فحص `npm audit --omit=dev` بعد التحديث صفر ثغرات تشغيلية معروفة. كما أصبحت أداة الاستعادة تتطلب `--confirm-drop=<اسم_قاعدة_البيانات>` وتنشئ نسخة PostgreSQL احتياطية مع SHA-256 قبل حذف أي قاعدة.

صُحح هدف خدمة Windows ليشغّل `AlShorfaERP.exe --service`، وهو الاسم نفسه المعرّف في إعدادات Electron Builder. عند بناء Installer على Windows، تحقق بعد التثبيت من أن مسار التطبيق يحتوي `AlShorfaERP.exe` وأن خدمة `AlShorfaERP` تعمل من Services بعد إعادة تشغيل الجهاز.

> ملاحظة تسليم: تم التحقق من مصدر الحزمة والبناء والاختبارات داخل Linux. بناء EXE وNSIS الفعلي واختبار الخدمة والطباعة يتطلب Windows، ولا ينبغي ادعاء اجتيازه قبل تشغيل `npm run build:exe` واختبار الناتج على جهاز Windows نظيف.

## قبول التهيئة الأولى وحزمة Windows المحدثة — 2026-08-24

كشف اختبار تهيئة PostgreSQL نظيف أن الترحيلة `030_dispatch_signatures_audit_periods.sql` كانت تعدّل جدول `kitchen_audits` قبل إنشائه في قاعدة بيانات جديدة. صُححت الترحيلة لتنشئ جداول تشغيل المطبخ بصورة idempotent قبل تعديلها، وأضيف اختبار انحدار يمنع عودة هذا التسلسل الخاطئ.

اجتاز قبول PostgreSQL المعزول إنشاء قاعدة اختبار جديدة وتطبيق 31 ترحيلة إنتاجية من `001` إلى `032` مع استبعاد `006_demo_seed.sql` لالتزام الحزمة بعدم إدخال بيانات تجريبية. أكد الفحص أن مستخدم `admin` موجود، وأن كلمة مروره bcrypt وليست `1234`، وأن `must_change_password=true` قبل الدخول الأول، مع حفظ بيانات البدء في موضع اختبار محلي مقيد فقط.

اجتاز قبول HTTP المعزول كذلك فحص الصحة، وتسجيل الدخول الأول بحالة `PASSWORD_CHANGE_REQUIRED`، ومنع مسار تشغيلي برمز مقيد (`403`)، وتغيير كلمة المرور، ثم السماح بالمسار التشغيلي وتسجيل الدخول الطبيعي برمز تحديث. لم تُستخدم أي قاعدة بيانات أو بيانات اعتماد حية في هذه الاختبارات، وحُذفت عناقيد الاختبار بعد النهاية.
