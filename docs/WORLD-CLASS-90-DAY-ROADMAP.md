# خطة رفع Karim ERP إلى جاهزية إنتاج عالمية

**الهدف:** بناء منتج ERP موثوق وقابل للتوسع والإصدار عبر أسواق متعددة، من دون إعادة كتابة النظام أو إعلان امتثال غير مثبت.

## خط الأساس الذي فُحص

- مصدر الحزمة `package.json`: الإصدار `4.9.2`، Node.js `>=20.0.0`، وElectron `44.x`.
- الفرع الحالي `stabilization/pos-unification` وفيه تغييرات كثيرة غير ملتزمة؛ لا تعتبر هذه النسخة مرشح إصدار قبل مراجعة الفروق وتجميعها في PRs صغيرة.
- بوابة lint كانت تفشل بثلاثة تحذيرات في `backend/menu-board-routes.js`؛ أُصلحت بإضافة الأقواس، ثم نجحت البوابة بصفر أخطاء وتحذيرات.
- نجح `npm run test:type` بالوضعين العادي والصارم، ونجح فحص الأسرار للملفات المتتبعة وفحص Docker بصفر مشاكل.
- نجحت 5 اختبارات حالة المنيو و4 اختبارات توافق بيانات README مع الحزمة. لم تُشغّل مجموعة ERP كاملة؛ حارس الاختبارات يتطلب قاعدة `karim_erp_test` معزولة فعلًا.
- README كان يعرض إصدارًا ومتطلبات Node وElectron واسم مثبت قديمًا؛ تم توحيدها مع manifest واسم artifact الحالي، وأضيف اختبار يمنع رجوع الانحراف.
- المجلد المحلي احتوى على 126 نسخة احتياطية بحجم إجمالي يقارب 16.43GB، إضافة إلى ملفات محلية حساسة. لم تُفتح محتوياتها ولم تُنقل أو تُحذف.
- README يصف تكامل ZATCA بأنه قيد التطوير وغير معتمد للإنتاج؛ لا تُسوّق الفوترة على أنها معتمدة قبل الإثبات الرسمي.

## الأيام 1–14: حماية البيانات وإقفال بوابة الإصدار

### العمل

1. جرد الملفات الحساسة في مسار المشروع، ثم نقلها إلى مخزن بيانات خاص بصلاحيات وصول محدودة، لا إلى Git ولا إلى حزمة التثبيت.
2. مراجعة الأسرار المحلية والمتتبعة، وإبطال/تدوير ما ثبت نشره فقط وفق نافذة تغيير مع مالك الإنتاج؛ لا تدوّر مفاتيح الإنتاج عشوائيًا.
3. سياسة مقترحة مؤقتة: احتفظ بكل النسخ الحالية؛ بعد اختبار نسخة خارج الجهاز والاستعادة، استهدف 30 نسخة يومية و12 شهرية ونسخة خارجية مشفرة غير قابلة للتعديل. لا تُحذف نسخة قبل تأكيد مدة الاحتفاظ المحاسبي/القانوني واختبار الاستعادة.
4. اختبار استعادة نسخة منزوعة البيانات على قاعدة معزولة، ثم التحقق من تطابق الجداول والترحيلات وسلامة معاملات البيع والمخزون.
5. تجميد نقطة إصدار: فرع نظيف، تغييرات مصنفة حسب المهمة، وعدم تضمين `runtime/`, `var/`, قواعد البيانات أو ملفات الجهاز في الحزمة.
6. ضبط مصدر واحد للإصدار، وتوقيع مُثبتات Windows وAPK بمفاتيح محفوظة خارج المستودع، مع توثيق الاسترجاع عند فقد المفتاح.

### بوابة الخروج

- لا أسرار أو بيانات موظفين داخل المستودع أو حزمة الإصدار.
- نجاح استعادة موثق من نسخة احتياطية، لا مجرد نجاح إنشاء النسخة.
- جميع اختبارات CI الحالية خضراء على نسخة نظيفة، مع build قابل للتكرار وبصمة artifact مسجلة.

## الأيام 15–30: إثبات المسارات التشغيلية

### العمل

1. توفير قاعدة اختبار مؤقتة تحتوي بيانات اصطناعية فقط، ثم تشغيل مجموعة Jest كاملة واختبارات التكامل دون الوصول إلى الإنتاج.
2. إضافة E2E حرجة لرحلات: بيع/إلغاء/استرداد، إغلاق وردية، صرف/تحويل/جرد مخزون، رواتب/اعتماد إجازة، ونسخ/استعادة.
3. اختبار الترحيلات من قاعدة فارغة ومن نسخة قديمة مستعادة، مع تحقق من القفل والتراجع وعدم تسجيل ترحيل فاشل على أنه مطبق.
4. إعداد بيئة staging مطابقة للإنتاج، وقائمة فحص تثبيت وترقية على Windows وAndroid، وخطة rollback لكل إصدار.
5. تشغيل اختبارات حمل على أحجام مستخدمين متفق عليها، وجمع p95، ومعدل الأخطاء، وتأخر الطوابير، وتأخر outbox قبل تحديد SLO.
6. توحيد runbooks والملاحظات، وحذف التكرار فقط بعد مراجعة مالك كل ملف، لا عبر تنظيف تلقائي.

### بوابة الخروج

- الرحلات الحرجة موثقة ومختبرة ببيانات اصطناعية.
- الترقية والاستعادة والرجوع مجربة على staging.
- لا فشل جديد في lint/type/security أو اختبارات حرجة؛ لكل فشل معروف مالك وخطة إصلاح.

## الأيام 31–60: حدود الشركات والفروع والأسواق

### العمل

1. السوق الأول بعد السعودية هو مصر. حسم ما إذا كان النشر لمجموعة فروع أم SaaS متعدد العملاء، وتحديد نوع الممول والأنشطة قبل اختيار قواعد الضرائب. ملاحظات ETA الأولية في `docs/EGYPT-LOCALIZATION-DISCOVERY.md`.
2. مراجعة نموذج `tenant` و`branch` والهوية والصلاحيات في API وقاعدة البيانات؛ منع الوصول بين العملاء/الفروع باختبارات سلبية لكل مسار حساس.
3. وضع واجهة adapter للضرائب والفوترة والدفع حسب البلد، مع مسارين منفصلين مبدئيًا لفاتورة B2B وإيصال B2C في مصر؛ لا تُنشر افتراضات السوق السعودي داخل منطق البيع والمحاسبة.
4. فصل العملة والمنطقة الزمنية والتقويم والتنسيق عن منطق الحسابات، وتحديد الإعدادات المصرية مع المحاسب؛ أضف اختبارات حدود اليوم/منتصف الليل والتحويلات المالية.
5. تعريف سياسة ترحيل بيانات العملاء وتصديرها وحذفها، وسجل تدقيق غير قابل للتلاعب لعمليات البيع والمخزون والرواتب.
6. اختبار العربية/الإنجليزية وRTL/LTR وإمكانية الوصول على أجهزة الكاشير والهواتف والشاشات المستخدمة ميدانيًا.

### بوابة الخروج

- إثبات عدم تسرب سجل بين عميلين أو فرعين في اختبارات التكامل.
- قواعد الضرائب والعملات والتوقيت موثقة لكل سوق إطلاق، ومراجعة من محاسب/مختص محلي.
- لا تُفعّل multi-tenant أو تغيير مخطط واسع قبل نجاح الترحيل والرجوع على نسخة مماثلة للإنتاج.

## الأيام 61–90: الاعتماد والإطلاق المحدود

### العمل

1. إكمال متطلبات ZATCA للسعودية وتكامل ETA لمصر في البيئات التي توفرها الجهات، واختبار الشهادات والتوقيع الإلكتروني والرفض وإعادة الإرسال، ثم الحصول على القبول المطلوب قبل ادعاء الاعتماد.
2. إجراء مراجعة أمنية مستقلة واختبار اختراق يشمل صلاحيات المستخدم، عزل الفروع، رفع الملفات، جلسات JWT، تحديث التطبيق، وحماية مفاتيح التوقيع.
3. مراجعة متطلبات الخصوصية المحلية لكل سوق، بما فيها الغرض والاحتفاظ والتصدير والحذف والوصول إلى بيانات الموظفين؛ طلب رأي قانوني عند الحاجة.
4. تشغيل تجريبي محدود مع مستخدمين حقيقيين بموافقة الإدارة، قناة دعم، جمع أعطال منقحة من البيانات الحساسة، وتراجع سريع.
5. نشر مؤشرات صحة ومراقبة: توافر API، أخطاء المبيعات، تأخر الطوابير/outbox، فشل النسخ، مساحة التخزين، واستهلاك قاعدة البيانات.
6. نشر دليل مستخدم وتشغيل وترقية واستعادة، سجل تغييرات، سياسة دعم، وخطة استمرارية أعمال.

### بوابة الإطلاق

- قبول رسمي لكل تكامل منظم يُعلن عنه، بما فيه ZATCA في السعودية وETA في مصر.
- مراجعة أمنية مستقلة بلا ثغرات حرجة/عالية غير مقبولة.
- اختبار استعادة ناجح، إصدار موقع، مراقبة وتنبيه، وخطة رجوع مجربة.
- تشغيل تجريبي مستقر خلال مدة متفق عليها، مع توقيع مالك المنتج والعمليات.

## ما يحتاج قرارًا أو وصولًا خارجيًا

- نقل أو حذف ملفات الموظفين والنسخ الاحتياطية يتطلب تحديد وجهة التخزين وسياسة الاحتفاظ والمخولين؛ لن تُحذف النسخ الموجودة تلقائيًا.
- تدوير أسرار الإنتاج يتطلب تحديد النظام المتأثر ومالك الخدمة ونافذة تغيير، ثم التحقق من نجاح الأجهزة والعملاء بعد التدوير.
- اعتماد ZATCA وETA، مراجعة ضريبية/قانونية مصرية، اختبار اختراق مستقل، ومفاتيح/شهادات التوقيع تتطلب الجهة المالكة أو مزودًا معتمدًا.
- تنفيذ تصميم عالمي متعدد العملاء يتطلب تحديد الدول والفروع ونمط الاستضافة والضرائب والعملات قبل تعديل قاعدة البيانات أو صلاحيات الوصول.

## ترتيب التنفيذ الفوري

1. اعتماد سياسة البيانات والنسخ ومراجعة الملفات الحساسة.
2. إنشاء قاعدة اختبار معزولة وتشغيل مجموعة ERP كاملة.
3. تنظيف تغييرات الفرع وتقسيمها، ثم جعل CI وبناء الإصدار الموقع قابليْن للتكرار.
4. إتمام قبول المبيعات والمخزون والرواتب والفوترة على staging.
5. بدء تصميم multi-tenant/الأسواق بعد اعتماد المتطلبات، ثم إطلاق تجريبي محدود.
